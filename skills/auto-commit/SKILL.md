# Auto Commit

## Overview

Turn a dirty working tree into a small series of clean, self-contained
Conventional Commits. Read the changes, group them by the work they do, stage
each group precisely, and commit it with a message that carries no trace of
having been written by an agent.

## Workflow

### 1. Survey the repository

Run these read-only commands before deciding anything:

```sh
git rev-parse --show-toplevel
git branch --show-current
git status --porcelain=v1 --untracked-files=all
git diff
git diff --staged
git log --oneline -20
```

Read `git log` to match the repository's existing conventions — scope naming,
capitalization after the colon, whether scopes are used at all. The repository's
convention wins over personal preference.

Stop and report instead of committing when:

- the directory is not a Git repository;
- there is nothing to commit;
- a merge, rebase, cherry-pick, or bisect is in progress;
- the diff contains what appear to be credentials, tokens, or `.env` values.

### 2. Read the diff, not the file list

Grouping decisions depend on what the change *does*. File names are not enough.
For large diffs, read them per path (`git diff -- <path>`) rather than skimming a
truncated whole.

### 3. Split the work into commits

One commit is one coherent unit of work. Split on **intent**, not on file count:

- A feature and the refactor that made room for it are two commits.
- Unrelated `chore` or formatting work is its own commit, never a passenger on a
  `feat`.
- A fix and the test that proves it belong in the *same* commit.
- Lockfiles, generated files, and snapshots ride with the change that caused
  them.
- Two unrelated fixes are two commits — unless both live in the same file, which
  stays whole and goes in one commit.

#### Files that describe other changes

Judge a file by what it does, not by its extension. A `.md` file is not
automatically `docs` work.

- **Release notes come last, once, for the whole batch.** A Changesets entry, a
  changelog line, or a release note describes the *set* of commits just made, so
  it cannot live inside one of them. Write a single entry as the final commit of
  the chain, summarizing everything in the batch. Never fold one into the feature
  commit it announces: the feature commit says what changed, the release note says
  what shipped. Use `chore:` for entries a tool consumes (`.changeset/*.md`) and
  `docs:` for a hand-maintained `CHANGELOG.md` that people read.
- **Rides with the change it explains.** A migration note or a decision record
  written to justify *this* change is part of it, and goes in the same commit
  under that commit's type.
- **Its own `docs:` commit.** Documentation that is itself the deliverable: a
  README, a guide, a reference page, a typo fix.
- **Not yours to commit.** A `CHANGELOG.md` or version bump generated by
  `changeset version`, `semantic-release`, or similar. Release tooling writes
  those in its own commit. If one is dirty in the working tree, leave it alone and
  say so in the summary.

Only write a release note when the repository already uses that system and the
batch warrants one. Do not introduce a changelog convention a repository does not
have.

Order the commits by dependency, not by type. Apply this test to each commit in
turn: does it reference a file, script, package, or command that no earlier commit
has introduced? If so, it belongs later.

Type is only a tie-breaker. When no commit depends on another, config and
dependency changes first, then refactors, then features and fixes, then docs.

Config is not automatically first. CI and release configuration is the common
trap: it reads like config, but a workflow that runs a build, a lint, or a test is
a *consumer* of everything that build touches, so it belongs after the code and
scripts it invokes.

Do not split when the result would be a commit that cannot stand alone — a
commit that fails to build or leaves a half-wired call site is worse than a
commit that is slightly broad.

Do not ask the user to approve the split, however many commits it produces. The
point of this skill is to get good commits made quickly; step 7 is where the user
reviews the result, and unpushed commits are cheap to redo.

### 4. Stage precisely

- Stage by explicit path: `git add -- <path> ...`. Never `git add -A`,
  `git add .`, or `git add -u`.
- **If anything was already staged before this skill ran, stop and ask.** Do not
  unstage it and do not fold it into a commit on an assumption. Show what is
  staged and ask whether to commit it as its own commit, include it in one of the
  planned commits, or leave it staged and untouched. Wait for an answer.
- Never discard work. No `git checkout --`, `git restore`, `git clean`,
  `git stash drop`, or `git reset --hard`.
- Untracked files: include one only when it belongs to the commit. Ask before
  committing anything that looks like a secret, a build artifact, or a local
  scratch file.
- Never split a file across commits. A file is always staged whole, in the commit
  it is most relevant to. Do not use `git add -p`, and do not hand-edit patches to
  stage individual hunks.

After staging, review `git diff --staged` and confirm it contains exactly the
intended change before writing the message.

### 5. Write the message

```
<type>[(<scope>)][!]: <description>
```

- **Types**: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`,
  `build`, `ci`, `chore`, `revert`.
- **Description**: imperative mood ("add", not "added" or "adds"), no trailing
  period, aim for 50 characters and never exceed 72.
- **Scope**: optional. Use a real module, package, or directory name. Omit it
  rather than inventing something vague.
- **Breaking changes**: mark with `!` before the colon. Always use `!`; never
  emit a `BREAKING CHANGE:` footer.

**Body — omit it by default.** Add one only when:

- the *why* cannot be recovered from the diff (a non-obvious constraint, a
  workaround, a decision that looks wrong without context); or
- the commit needs an issue footer, since a footer is only permitted alongside a
  body.

When a body is present: one blank line after the subject, wrapped at 72
characters, stating the reason rather than restating the diff.

**Footer — the only permitted footer is an issue reference** for an issue this
commit addresses: `Closes #42`, `Fixes #42`, or `Refs #42`, after a blank line
following the body. Take the issue number only from an explicit instruction or
from a branch name that encodes it. Never guess at one, and never add a footer
without a body.

**Never appears anywhere in the message:**

- `Co-authored-by:` naming an agent, model, or tool
- "Generated with", "Assisted-by", "Written by", or any model or tool name
- `Signed-off-by:` unless the user asks for it
- Emoji, unless the repository's own history uses them
- "This commit…", "I", "we", or a restatement of the file names

The message must read as though the author wrote it by hand.

### 6. Commit and verify

- Commit with one `-m` per block:
  `git commit -m "<subject>" -m "<body>" -m "<footer>"`.
- Never pass `--no-verify`. If a hook rewrites files, re-`git add` the same paths
  and retry the commit once; if it fails again, stop and report the hook output.
- Never `--amend` a commit that existed before this skill ran.
- Repeat steps 4–6 for each remaining group.

Commits stay local. Nothing is pushed in this step.

### 7. Summarize, then ask about pushing

Print a summary short enough to read in one glance — one line per commit, subject
only, plus one line for anything still uncommitted:

```
3 commits on feat/refresh-tokens:

  a1b2c3d  refactor(auth): extract token parsing into a helper
  d4e5f6a  feat(auth): support refresh tokens
  7b8c9d0  docs: document the refresh token flow

Uncommitted: 1 file (notes.local.md, untracked)
```

Then ask whether to push. Push only on an explicit yes, and only with a plain
`git push`. Never `--force`, `--force-with-lease`, or a refspec that targets a
branch other than the current one. If the current branch is the default branch,
say so when asking.

Because these commits are local and unpushed, they are still yours to fix. If the
user rejects the split, `git reset --soft <hash-before-the-first-new-commit>` to
return every change to the index, then restage and redo. This is the one case
where undoing commits is permitted, and it only ever applies to commits created
in this session and never pushed. Confirm the reset with the user first, and
never use `--mixed` or `--hard`.

## Examples

A tidy split from one dirty tree:

```
refactor(auth): extract token parsing into a helper
feat(auth): support refresh tokens
docs: document the refresh token flow
```

A body only where it earns its place:

```
fix(api): retry profile fetch on 502

Upstream returns a 502 for roughly one request in a thousand during
deploys, which surfaced as a blank profile screen.

Closes #128
```

A breaking change, with no footer needed:

```
feat(api)!: rename /v1/orders to /v1/checkout
```

Subject only, because the diff already says everything:

```
chore: bump eslint to 9.13.0
```
